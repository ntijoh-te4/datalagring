= Vyer och stored procedures i praktiken

Två SQL-konstruktioner som inte kommer upp i SQLBolt, men som båda finns med i centralt innehåll för Datalagring nivå 2.

== Vyer

En *vy* (engelska: view) är en _virtuell_ tabell som definieras av en `SELECT`-fråga. Vyer lagrar ingen egen data — varje gång man läser ur vyn kör databashanteraren den underliggande frågan.

=== Skapa en vy

[source,sql]
----
CREATE VIEW active_students AS <1>
SELECT id, first_name, last_name, class_id
FROM students
WHERE active = TRUE;
----
<1> Vyn `active_students` är nu åtkomlig som om den vore en tabell.

Man kan sedan använda vyn precis som vilken tabell som helst:

[source,sql]
----
SELECT * FROM active_students WHERE class_id = 7;
----

=== Varför vyer?

. *Förenkla komplexa frågor.* Om en applikation upprepade gånger kör en stor `SELECT` med flera `JOIN` är det bekvämt att lägga frågan i en vy och låta applikationen läsa från vyn istället.
. *Säkerhet och åtkomstkontroll.* En vy kan exponera en _delmängd_ av en tabells kolumner. Eleverna får läsa från `students_public` (utan personnummer) men inte direkt från `students`.
. *Abstraktion.* Underliggande tabellstruktur kan ändras utan att applikationen märker det — så länge vyn levererar samma kolumner.

=== Materialiserade vyer

En vanlig vy kör om sin underliggande fråga vid varje läsning. En _materialiserad_ vy lagrar resultatet och uppdateras periodiskt.

[source,sql]
----
CREATE MATERIALIZED VIEW class_statistics AS <1>
SELECT class_id, COUNT(*) AS student_count, AVG(grade) AS avg_grade
FROM students
GROUP BY class_id;

REFRESH MATERIALIZED VIEW class_statistics; <2>
----
<1> Resultatet beräknas en gång och lagras.
<2> När underliggande data ändrats måste vyn refreshas manuellt (eller via en trigger eller cron-job).

Användbart när den bakomliggande frågan är dyr men datan inte behöver vara helt färsk.

== Stored procedures i praktiken

Som diskuterades i kapitel 2 är en *stored procedure* kod som lagras direkt i databashanteraren och kan anropas vid behov. Här ser vi hur det ser ut i praktiken (PostgreSQL och PL/pgSQL):

=== Skapa en funktion

[source,sql]
----
CREATE OR REPLACE FUNCTION transfer_money( <1>
    source_id INT,
    target_id INT,
    amount NUMERIC
) RETURNS VOID AS $$
BEGIN
    UPDATE accounts SET balance = balance - amount WHERE id = source_id; <2>
    UPDATE accounts SET balance = balance + amount WHERE id = target_id;
END;
$$ LANGUAGE plpgsql;
----
<1> Funktionen tar tre parametrar.
<2> Hela funktionen körs i en _implicit_ transaktion — antingen lyckas båda UPDATE eller ingen.

=== Anropa funktionen

[source,sql]
----
SELECT transfer_money(1, 2, 500);
----

Funktionen körs på databas­servern. Applikationen behöver bara skicka ett anrop över nätverket — själva logiken (de två UPDATE-satserna) sker lokalt i databasen.

=== Triggers

En *trigger* är en stored procedure som körs _automatiskt_ när något händer i en tabell.

[source,sql]
----
CREATE TRIGGER log_grade_change <1>
AFTER UPDATE ON grades <2>
FOR EACH ROW
EXECUTE FUNCTION write_audit_log(); <3>
----
<1> Triggern heter `log_grade_change`.
<2> Den körs efter varje `UPDATE` på `grades`-tabellen.
<3> För varje uppdaterad rad anropas den tidigare definierade funktionen `write_audit_log`.

Triggers är användbara för att upprätthålla invarianter, logga ändringar, eller automatiskt uppdatera relaterade tabeller — men kan också göra applikationen svår att felsöka eftersom logik försvinner ner i databasen.
